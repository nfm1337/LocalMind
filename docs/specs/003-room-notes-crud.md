# Spec: Notes Room CRUD

## Status

Draft

## Current Phase

Phase 2A — real local notes without RAG persistence.

## Goal

Add real user notes persisted with Room and provide a minimal notes list/editor flow.

This spec creates the local notes foundation for future RAG indexing, but it does not generate embeddings or perform semantic search yet.

## Context

The hardcoded RAG slice already proves the basic retrieve → prompt → generate path. The next step is to replace hardcoded notes with real user-created notes, but without mixing persistence work with embedding/indexing work.

Room is the chosen persistence layer for MVP. ObjectBox and vector databases are not used.

## Non-Goals

- Embeddings
- Chunking
- Semantic search over Room notes
- Ask over real notes
- ObjectBox
- Vector database
- Background indexing
- FTS
- Import/export
- Tags/folders
- Rich text editor
- Cloud sync
- Login

## User / Developer Flow

1. User opens the app.
2. User sees a list of saved notes.
3. User creates a new note.
4. User enters title and content.
5. User saves the note.
6. Note appears in the list.
7. User can reopen and edit the note.
8. User can delete the note.
9. Notes remain after app restart.

## Requirements

- Add Room database for notes.
- Add `NoteEntity`.
- Add DAO methods for:

    - observe all notes;
    - get note by ID;
    - insert/update note;
    - delete note.
- Add repository abstraction for notes.
- Add minimal domain model if current architecture uses domain models.
- Add notes list UI.
- Add note editor UI.
- Validate empty notes:

    - completely empty note should not be saved;
    - title may be empty if content exists;
    - content may be empty if title exists.
- Notes should be sorted by `updatedAt` descending.
- Existing hardcoded RAG flow must not be broken by this spec.

## Data / State

Room becomes the source of truth for real user notes.

Suggested entity:

```kotlin
@Entity(tableName = "notes")
data class NoteEntity(
    @PrimaryKey val id: String,
    val title: String,
    val content: String,
    val createdAt: Long,
    val updatedAt: Long
)
```

For this spec, there are no chunks and no embeddings.

## UX Notes

Minimal UI is enough:

* notes list;
* create note action;
* note editor;
* save/delete actions;
* empty state.

No rich text, search, tags, folders, or advanced polish.

## Technical Notes

* Use Room only.
* Do not introduce ObjectBox.
* Do not add embedding storage yet.
* Keep note persistence independent from the hardcoded RAG retriever.
* Prefer small, testable repository/use case boundaries.
* If navigation does not exist yet, add only the minimum needed for list/editor.
* Do not remove the hardcoded RAG screen unless explicitly decided.

Potential impacted files/modules:

* Room database setup
* `NoteEntity`
* `NoteDao`
* notes repository
* notes ViewModel
* notes list screen
* note editor screen
* DI module for database/repository

## Metrics

No AI metrics required.

Optional:

* note save latency if easy to log.

## Acceptance Criteria

- App builds and runs.
- User can create a note.
- User can edit a note.
- User can delete a note.
- Notes persist after app restart.
- Empty note cannot be saved.
- Notes are sorted by updated date.
- Hardcoded RAG flow still works.
- No embeddings/chunks/vector search are introduced.

## Risks

- UI/navigation scope may grow too much.
- Existing `Note` model for hardcoded dataset may conflict with Room note naming.
- Adding Room may require Gradle/schema setup.
- This spec may accidentally couple note CRUD to RAG indexing too early.

## Open Questions

- Should hardcoded demo notes and user notes share one domain model name?
- Should note IDs be UUID strings or autogenerated Long IDs?
- Should note editor autosave or explicit save? For MVP, explicit save is simpler.
